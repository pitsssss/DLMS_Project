# POSTMAN API GUIDE - DLMS / SYRTAK

## 1) Import and Setup
- Import `DLMS_API_Postman_Collection.json` into Postman.
- Collection variables:
  - `base_url = http://127.0.0.1:8000`
  - `api_prefix = /api`
- Keep all token variables empty initially (`citizen_token`, `employee_token`, `admin_token`, and role-specific dashboard tokens).

## Collection Layout
Top-level folders:
1. `00. Public & System` — ping, public content, reference data, license verify
2. `01. Citizen App` — all citizen modules (Auth → Profile → Applications → … → AI Agent)

## 3.1) Citizen Notification Center (Flutter)
Final 4-operation contract (`auth:sanctum` + `locale` + `citizen`):

| Action | Method | Path |
|--------|--------|------|
| List inbox | `GET` | `/api/notifications?page=1&per_page=20` |
| Bell badge | `GET` | `/api/notifications/unread-count` |
| Mark one | `PUT` | `/api/notifications/{id}/read` |
| Mark all | `PUT` | `/api/notifications/read-all` |

Notes:
- Auth: `auth:sanctum` + `locale` + `citizen`. No Firebase / FCM delivery yet — in-app DB notifications only.
- Query: `per_page` (default 20, max 100), `unread_only` (optional boolean). Do not derive badge count from the list.
- Resource fields: `id`, `title`, `body`, `type`, `read_at`, `is_read`, `data`, `created_at`. Navigate with `type` + `data` (never parse localized title/body for routing).
- `event_key` / `user_id` are never exposed. Historical `title`/`body` stay as stored text (recipient `users.language` at write time); `Accept-Language` localizes envelope messages only and does **not** retranslate past notifications.
- Source Flutter collection: `postman/SYRTAK_Flutter_API.postman_collection.json` (folder `10 - Notifications`).

## 3.2) Citizen Push Device Registration (F1 — no FCM send yet)

Minimal Flutter contract (`auth:sanctum` + `locale` + `citizen`):

| Action | Method | Path |
|--------|--------|------|
| Register / rotate token | `POST` | `/api/devices/push-token` |
| Unregister this installation | `DELETE` | `/api/devices/push-token` |

### Flutter lifecycle (later Firebase Messaging phase)

1. **After login / app start:** Flutter obtains an FCM registration token → `POST /api/devices/push-token` with `{ "device_id", "platform", "token" }`.
2. **Token refresh:** Same endpoint with the **same** `device_id` and the **new** `token` (no separate refresh API).
3. **Multiple devices:** Each app installation registers independently (own `device_id` + token). Future push delivery will target all active devices for the citizen.
4. **Logout:** `DELETE /api/devices/push-token` with `{ "device_id" }` for **this** installation, then normal `POST /api/auth/logout`. Logging out phone A must not unregister phone B. Auth logout itself is unchanged and does not clear all devices.

### Request / response notes

- `device_id`: opaque **app-installation** ID generated by Flutter (UUID). Do **not** use IMEI, MAC, serial, or other hardware identifiers.
- `platform`: machine value only — `android` or `ios` (never translated).
- `token`: FCM registration token. Backend stores it encrypted; **never** returned in API responses; never logged.
- Register success `data`: `{ device_id, platform, registered: true }`.
- Unregister success `data`: `{ device_id, unregistered: true }` (idempotent).
- Envelope `message` follows `Accept-Language` (AR/EN). In-app Notification Center remains the source of truth; Firebase push is a supplementary channel when `FIREBASE_PUSH_ENABLED=true` and a push queue worker is running.
- Env vars in Postman: `push_device_id`, `fcm_token` (placeholder only — no real FCM token in the collection). The actual `fcm_token` is supplied by Flutter Firebase Messaging in a later phase.

## 3.3) Firebase server transport (F2 — internal only)

Backend-only infrastructure. **No public HTTP API** for sending pushes.

| Concern | Detail |
|---------|--------|
| Env | `FIREBASE_PROJECT_ID`, `FIREBASE_CREDENTIALS_BASE64` (Base64 of service-account JSON; **secret** — Base64 is encoding, not encryption). Optional: `FIREBASE_CA_BUNDLE` absolute CA path when `php.ini` `curl.cainfo` is unset (common on Windows). Fallback file: `storage/app/private/certs/cacert.pem` (not committed). |
| Ops check | `php artisan firebase:verify` — validates credentials + Google OAuth; never prints tokens/keys |
| Transport | FCM HTTP v1 via Google Auth (`google/auth` ^1.53) + Laravel HTTP client |

Do **not** add Postman test-send requests. Do **not** put credentials in collections or docs.

## 3.4) Queued push delivery (F3/F4 — internal only)

After a **new** DB notification is created (not an `event_key` dedupe reuse):

1. Plan one `push_deliveries` row per registered `push_devices` for that citizen.
2. Dispatch `SendPushNotificationJob` on queue `push` (delivery ID only — never the FCM token).
3. Worker loads current encrypted token → `FcmClient` → FCM.

| Concern | Detail |
|---------|--------|
| Env | `FIREBASE_PUSH_ENABLED=false` by default (`filter_var` boolean). Production: `true` + `QUEUE_CONNECTION=database` + worker. |
| Worker startup | `docker/php/entrypoint.sh` → `exec supervisord` → `[program:queue-push]` (`autostart`/`autorestart`). |
| Worker | `php artisan queue:work --queue=push,default --tries=25 --timeout=60` |
| Timeouts | FCM HTTP `15s` &lt; job `60s` &lt; `DB_QUEUE_RETRY_AFTER=120` |
| FCM attempts | `push_deliveries.attempts` capped by `FIREBASE_PUSH_TRIES=5` (real sends only) |
| Laravel tries | `FIREBASE_PUSH_JOB_MAX_TRIES=25`; overlap uses `WithoutOverlapping::dontRelease()` |
| Recovery | `php artisan push:dispatch-pending` — pending redispatch + stale `processing` lease reclaim |
| Failed jobs | `queue:failed` / `queue:retry` / `queue:forget` — payload is delivery ID only |
| Failure rule | FCM / queue failure **never** deletes or rolls back the DB notification |
| Title/body | Taken from the stored notification (recipient `users.language` at create time). No second translation path. |
| Data | `notification_id`, `type`, plus safe notification `data` keys as strings |

After Flutter registers via `POST /api/devices/push-token`, future in-app notifications become push-eligible when push is enabled and a worker is running. Real device send remains pending a Flutter FCM token.

## 6) File Upload Guidance
- Endpoints use `form-data`.
- Use:
  - `required_document_id` (text)
  - `file` (file picker in Postman)
- Do not manually set `multipart/form-data` content type; Postman generates boundary.
- Use test files only (no private sensitive files).

## 7) Error and Security Scenarios
- Folder `28. Error & Security Scenarios` includes ready-to-run examples for:
  - `401` unauthenticated
  - `403` wrong role
  - `422` validation failure
- Additional security checks can be run by calling foreign resource IDs (`foreign_application_id`, etc.) to verify `403/404` behavior.

## 8) Variables and Auto-ID Behavior
- Collection has IDs for citizen/applications/documents/payments/appointments/licenses/fines/AI sessions/actions.
- Some create/login requests automatically store IDs/tokens using test scripts.
- Pre-request script updates `unique_suffix` (timestamp) for generating non-colliding demo values.
